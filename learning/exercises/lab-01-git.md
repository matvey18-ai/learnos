# ЛР №1 — Введение в систему контроля версий Git

> Черновик-конспект подготовлен LLM (2026-10-02) по методичке, PDF стр. 4–17. Сверь с оригиналом, перепиши «Теорию» и ответы своими словами перед сдачей. Файл методички в репозиторий не добавлен.

## Цель

Понять, зачем нужен контроль версий, и освоить базовые операции Git через командную строку: создание репозитория, индекс, коммиты, история, ветки, слияние и отмена изменений.

## Теория — ключевое своими словами

- **Зачем VCS:** копии вида «Диплом_финал_2.docx» не отвечают, что актуально, кто и когда менял и как вернуться назад. VCS хранит историю изменений файлов и управляет версиями.
- **Git vs GitHub:** Git — программа, стоящая на компьютере, работает локально без интернета; GitHub — один из интернет-сервисов для хранения репозиториев (есть также GitLab, GitFlic, Bitbucket). Это разные вещи.
- **Три зоны:** рабочий каталог (файлы, которые ты правишь) → `git add` → индекс (отбор изменений в следующий коммит) → `git commit` → история. Важно: `add` ещё ничего не сохраняет — оно лишь решает, что попадёт в коммит.
- **Коммит** — логически завершённое изменение с хэшем, автором и датой; сообщение объясняет, что изменено («Добавлена обработка ввода»), а не «commit1».
- **Состояние:** `git status` — что изменено/не отслеживается/в индексе и какая ветка; `git diff` — ещё не добавленные изменения, `git diff --staged` — подготовленные.
- **Ветка** — указатель на коммит, отдельная линия развития (основная — `main`). `merge` объединяет; при конфликте Git сохраняет обе версии и маркеры `<<<<<<< / ======= / >>>>>>>`, потому что финальное решение — за человеком. Конфликт — не ошибка Git.
- **Отмена — три разных действия под фразой «отменить»:**
  - `git restore file` — вернуть файл к последнему коммиту (незакоммиченные правки пропадают);
  - `git restore --staged file` — убрать из индекса, сам файл не меняется;
  - `git revert commit` — создать новый коммит, отменяющий старый; история остаётся целой.
- **revert vs reset:** revert добавляет «противо-коммит» и безопасен; `git reset --hard` перемещает указатель ветки и меняет историю — опасно, в этой лабе не используется.
- Настройка: `git config --global user.name/user.email`, проверка `git --version`, `git config --list`.

## Практическая часть (10 заданий, кратко)

1. Каталог `git_lab` → `git init` → `git status`.
2. Файл `notes.txt` («Первая версия файла») → status → `git add` → первый коммит → `git log` / `git log --oneline`.
3. Дописать строки → `git diff` → add → `git diff --staged` → второй коммит (сообщение придумать самому).
4. Ещё ≥3 последовательных изменений, каждое — отдельным коммитом; итого **≥5 коммитов**.
5. Ветка `experiment`: файл `experiment.txt`, коммит; возврат в `main` — объяснить, почему файла в `main` нет.
6. `git switch main` → `git merge experiment` → проверить файл и историю.
7. Откат незакоммиченной правки `notes.txt` через `git restore`.
8. add → `git restore --staged` → ответить: удалилось ли само изменение файла?
9. Коммит «Экспериментальное изменение» → `git revert <id>` → ответить: исчез ли коммит из истории?
10. Самостоятельно: своя ветка → файл → 2 коммита → посмотреть различия → merge в `main` → итоговая история.

## Требование к результату

Уметь объяснить назначение команд `init, status, add, commit, log, diff, branch, switch, merge, restore, revert` и различать: Git/GitHub, рабочий каталог/индекс, файл/коммит, коммит/ветку, отмену изменений/изменение истории.
